## 第10章：模型上下文协议

要使大语言模型作为智能体有效运作，其能力必须超越多模态生成。与外部环境的交互是必要的，包括访问当前数据、使用外部软件，以及执行特定操作任务。模型上下文协议（MCP）通过为大语言模型提供与外部资源交互的标准化接口来满足这一需求。该协议是促成一致且可预测集成的关键机制。

### 模型上下文协议模式概览

设想一个通用适配器，允许任何大语言模型接入任何外部系统。此外，模型上下文协议还可以封装输入或输出对智能体而言仍不易理解的 API。只有当 API 的数据格式对智能体友好时，它才有用，而模型上下文协议本身并不强制提供这种保证。例如，为一个以 PDF 形式返回文件的文档存储创建模型上下文协议服务器，若消费端智能体无法解析 PDF 内容，则基本没有用处。更好的做法是先创建一个返回文档文本版本（例如 Markdown）的 API，这样智能体才能真正阅读和处理。这说明开发者不仅要考虑连接本身，还必须考虑所交换数据的性质，以确保真正的兼容性。

### 模型上下文协议与工具函数调用

模型上下文协议（MCP）与工具函数调用是不同的机制。以下是模型上下文协议与工具函数调用之间的基本区别：

**特性** **工具函数调用** **模型上下文协议（MCP）**

**标准化** 专有且特定于供应商。格式与实现因大语言模型提供商而异。开放的标准化协议，促进不同大语言模型与工具之间的互操作性。

**范围** 大语言模型请求执行特定功能的直接机制。更广泛的框架，用于大语言模型与外部工具如何相互发现与通信。简言之，函数调用提供对少数特定函数的直接访问，而模型上下文协议是标准化的通信框架，让大语言模型能够发现并使用大量外部资源。对于简单应用，特定工具已足够；对于需要适应的复杂互联 AI 系统，像模型上下文协议这样的通用标准至关重要。

### 模型上下文协议的其他考量

尽管模型上下文协议提供了强大的框架，全面评估仍需考虑若干影响其是否适合特定用例的关键方面。

让我们更详细地看一些方面：

● **工具 vs. 资源 vs. 提示词**：理解这些组件的具体角色很重要。资源是静态数据（例如 PDF 文件、数据库）。其架构允许在组织范围内对常用工具进行共享、可扩展的访问。

● **按需 vs. 批处理**：模型上下文协议可以同时支持按需交互式会话与更大规模的批处理。选择取决于应用场景，既可以是需要即时工具访问的实时对话智能体，也可以是按批次处理记录的数据分析流水线。

● **传输机制**：该协议还定义了通信所用的底层传输层。对于本地交互，它通过 STDIO（标准输入/输出）上的 JSON-RPC 实现高效的进程间通信。对于远程连接，它利用对 Web 友好的协议，如可流式 HTTP（Streamable HTTP）和服务器发送事件（SSE），以实现持久且高效的客户端-服务器通信。

模型上下文协议使用客户端-服务器模型来标准化信息。

2. **请求制定**：大语言模型判定需要使用某个已发现的工具。例如，它决定发送一封电子邮件。它会制定请求，指定要使用的工具（send_email）以及必要参数（收件人、主题、正文）。

3. **客户端通信**：模型上下文协议客户端接收大语言模型制定的请求，并将其作为标准化调用发送到相应的模型上下文协议服务器。

4. **服务器执行**：模型上下文协议服务器接收请求。它会认证客户端、校验请求，然后通过与底层软件交互来执行指定操作（例如调用邮件 API 的 send() 函数）。

5. **响应与上下文更新**：执行后，模型上下文协议服务器将标准化响应发送回模型上下文协议客户端。该响应表明操作是否成功，并包含任何相关输出（例如已发送邮件的确认 ID）。客户端再将此结果传回。相较于返回整份文档的传统搜索工具，智能体可以分析文本并提取直接回答用户复杂问题的精确条款、图表或陈述。

● **自定义工具开发：** 开发者可以构建自定义工具，并通过模型上下文协议服务器暴露它们（例如使用 FastMCP）。这使专用内部功能或专有系统能够以标准化、易于消费的格式提供给大语言模型和其他智能体，而无需直接修改大语言模型。

● **标准化的大语言模型到应用通信：** 模型上下文协议确保大语言模型与其交互的应用之间有一致的通信层。这减少了集成开销，促进不同大语言模型提供商与宿主应用之间的互操作性，并简化复杂智能体式系统的开发。

● **复杂工作流编排：** 通过组合各种模型上下文协议暴露的工具
